## Development gate

1. Limit each update to the requested feature or defect. Record the starting SHA, player journeys and affected dependencies before editing shared systems. Work on the development branch and retain the stable checkpoint.
2. Make minimal, isolated, reversible changes. Keep Android offline and phone-host assets in parity. Protect approved controls, smoothness, visuals, menus, maps, gameplay, settings, and device refresh, battery and thermal limits.
3. Run focused checks for changed behavior. Require the **Sightline approved baseline** Actions job to pass before promoting a candidate. It checks authored-map movement, touch ownership, startup, preferences, rendering policy, match rules, outbreak and loopback LAN. It does not build an APK.
4. For movement and performance changes, compare the same scenarios against DEV24.9 on matched conditions. A failing approved journey blocks promotion. Repair the affected path or restore its stable implementation and verify again.
5. Advance the protected baseline only after the owner accepts the exact candidate. Keep previous commits, artifacts and app data. Production still requires the existing fail-closed release gate.
6. Record original-asset creation evidence. Require documented commercial use, redistribution and applicable modification rights before introducing outside assets. Review only added or modified assets, dependent files, and changed distribution or licensing terms against the [rights register](RIGHTS-INVENTORY.md). Refer possible conflicts in approved assets to the owner before changing them.

## Movement evidence and next device comparison

The source replay uses production stick sampling, movement integration and authored map collision boxes in Courtyard and Horror City. Both Android trees are checked at simulated 60, 90 and 120 Hz. At 60 Hz, a 16 CSS px drag traveled 1.8207 m in DEV24.9 and 2.8244 m in DEV25.5 over two seconds. The precision-walk correction restores 1.8207 m and keeps the input continuous. Full-stick directions and the aimed turning course match DEV24.9. The fire check counts calls into the weapon path. It does not measure ballistics, Android input latency or physical FPS.

To repeat the commit comparison, set `SIGHTLINE_MOVEMENT_REFERENCE` to the full DEV24.9 SHA and run `node --test tests/mobile-movement-reference.test.cjs`. The lightweight CI check also pins measured trajectory values without fetching the reference history.

Before another performance APK is promoted, record the exact APK hash, phone and Android/WebView versions, refresh rate, preset, render scale and performance mode. Match the map, mode, roster and route, and start from comparable temperature and Battery Saver states. Check stationary aim, precision walk, full-stick strafe and sprint, turns while moving, and aiming and firing together. Save rendered FPS, P95/P99 frame intervals, spikes over 50 ms and any dropped or stuck touches. Device smoothness, sustained heat and Android ↔ Windows LAN remain open until measured.

## Galaxy A17 5G walking recovery candidate

DEV24.9 remains the owner-confirmed smooth Android reference. P11.5.7 is a source-verified historical lead. The current DEV26.5 diagnostic is preserved. The recovery candidate moves minimap obstacle binning to map setup. The previous lookup scanned the full obstacle list and allocated a replacement array when the player entered a new 8-unit cell. Stationary camera rotation reused the same cell. This work path predates DEV24.9, so it cannot by itself identify the later phone regression.

The existing approved regression job now compares stationary yaw and translation across radar cells under the same map and drawing settings. It requires zero live full-list scans in both scenarios and verifies obstacle draw parity across all authored maps and both web trees, including map changes and the out-of-bounds spectator fallback.

Before promotion, repeat stationary aim and walking while turning/firing/reloading on the Galaxy A17 5G in the reported map and mode, at matching cap, render scale, preset and refresh rate. Record exact build hash, control response, FPS, P95/P99 intervals, stalls over 50 ms and any remaining stutter. Repeat over Wi-Fi with the matching host only if offline is smooth. Keep DEV24.9 and the current diagnostic available for comparison and rollback.

The 24c9034–5bd1939 comparison found a reproducible low-travel stick-response change at 6a7f2e1 (DEV25.5). The subsequent cd6474d fix recovered the 16 px reference, but the magnitude clamp still reduced speed near the dead zone. On an unscoped 5.2 m/s weapon baseline, 8 px gave a 0.4727 m/s steady target on DEV24.9 and 0.4000 m/s on DEV26.5. The diagnostic candidate fades in the earlier walk curve over the first 3 px past the existing dead zone. At 8–16 px it restores the reference curve; beyond that it retains the accepted blend and sprint behavior.

Collision, floor and ceiling functions are byte-identical between DEV24.9 and DEV26.5. DEV25.0 changed texture setup at map construction; d07afb3 changed missed-render deadline handling. Neither change has been tied to the handset symptom. The low-travel deviation postdates the first DEV25.4 movement report, so this is a verified response repair and not a diagnosis of the original stutter. Keep physical acceptance pending and use the distinct p0-walk-diagnostic build for a matched A/B.
